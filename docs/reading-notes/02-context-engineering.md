# 第二篇：上下文工程 —— 决定 Agent 能力上限

> 原文：[走进 AI Agent 第二篇（掘金）](https://juejin.cn/post/7677562804154531890)，作者「老王以为」，2026-08。
>
> 核心观点：模型的能力是天花板，上下文的质量才是真正决定 Agent 能跳多高的地板。

## 上下文窗口的构成

```text
静态前缀：系统提示词 + 工具定义
动态部分：对话历史 + 状态栏
```

两个容易忽略的事实：

1. 模型是无状态的，框架每次必须重送完整历史。
2. 必须使用厂商标准 Chat Template，不要自行拼接字符串。

## KV Cache：隐形架构约束

- 系统提示词和工具定义一经确定不可改动，否则缓存全失效。
- 文中事故案例：在系统提示词里注入时间戳，导致首 token 延迟从 0.5 秒涨到 3-5 秒、账单翻倍。
- 动态信息永远追加到末尾，不动前缀。
- 区分推理引擎层的 KV Cache 与服务商层的 Prompt Cache。

工程结论：**会变的信息放尾部，不变的信息放前缀**。

## 提示工程要点

- 首先是产品设计问题：决策规则必须明确到可执行（例如退货审核 Agent 的三档判定）。
- 流程驱动（SOP）优于规则堆砌。
- Few-shot 示例要字节级稳定，两三个精选示例胜过十个相似示例。
- 提示注入分三类：直接注入、间接注入（藏在检索内容里）、记忆注入；需要来源标记、结构化角色、输入清洗，并配合执行层防御（权限、沙盒）。

## Agent Skills：按需加载

通过"渐进式披露"三层结构兼顾缓存效率与指令遵循：

```text
元数据路由 → 完整 SKILL.md → 子文档细则
```

类比 npm/pip 包管理：平时只加载"包名"，用到才展开内容。

## 状态栏：注意力擅长检索，不擅长提炼

- 让框架用代码（不是 LLM）提前算好状态（如"第 3/3 次呼叫"），以 user 消息形式注入上下文末尾。
- 实测效果：弱模型准确率提升 40-54 个百分点，强模型思考量下降约一个数量级。
- 工程经验：把状态栏准确率当生产指标盯；删除原始上下文前先确认状态栏已覆盖。

## 上下文压缩

- 区分两种问题：窗口溢出（装不下）和"上下文腐化"（装得下但找不到）。
- 六种策略中"上下文感知压缩"效果最佳（可将 147,877 字符压至约 1.3%）。
- 生产级五层机制：预算控制 → 噪声删除 → API 微压缩 → 归档式摘要 → 带熔断器的全量压缩。
- 压缩保留优先级：架构决策、变更记录、验证状态、TODO 必须保留；UUID、hash 等标识符必须原样保留。

## 子 Agent 隔离

- 用隔离代替压缩：大体积中间信息不进入主上下文，子 Agent 只回传结论性摘要。
- 对比：隔离是无损的事前预防，压缩是有损的事后补救。

## 五条结语

1. 上下文质量决定决策质量。
2. KV Cache 是铁律约束。
3. 注意力擅长检索，不擅长提炼。
4. 压缩是有损蒸馏，需要保优先级。
5. 隔离优于压缩。

引用 Sutton「苦涩的教训」：这些技术是当前模型边界下最大化信息利用效率的工程实践，而"主动提供经过提炼的结构化信息"这一原则会穿越模型迭代周期。
