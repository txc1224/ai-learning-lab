# 第 15 篇：从一个副标题字段看懂后端完整交付链路

> 原文：[从一个副标题字段看懂后端完整交付链路](https://juejin.cn/post/7668198031946809380)，作者 swipe，《从前端到全栈：Spring Boot 项目实战通关》。
>
> 本笔记是蒸馏版，只保留核心问题、概念和结论，细节请读原文。

## 核心问题

前端人常以为"后端加个字段就是改一行代码"。这篇文章用"给商品加一个副标题（subtitle）"这个最小需求，拆解后端从数据库到接口再到前端联调的完整交付链路，回答：一个看似微小的字段变更，为什么要穿过那么多层？

## 关键要点

- **一个字段的完整路径（缺一层字段就在那层消失）**
  1. 数据库表结构（migration）
  2. Entity（ORM 实体，映射表）
  3. DTO（对外传输对象，定义接口契约）
  4. Service（业务逻辑透传/加工）
  5. Controller（出入参）
  6. 接口文档 + 前端联调

- **数据库迁移（migration）**
  - 改表不能手动改库，要写迁移脚本，如：

  ```sql
  ALTER TABLE product ADD COLUMN subtitle VARCHAR(100) NULL;
  ```

  - 迁移文件进版本库，保证开发/测试/生产按同一顺序演进表结构。
  - 新字段尽量可空或带默认值，避免历史数据刷不过去。

- **Entity 与 DTO 分开的原因**
  - Entity 对应表结构，DTO 对应接口契约；直接把 Entity 抛给接口会暴露内部字段（软删除标记、内部状态等）。
  - "副标题只在管理端 DTO 出现、不出现在 C 端 DTO"这类需求，正是靠分层实现的。

- **参数校验跟着字段走**
  - DTO 上加校验（是否必填、长度上限），Controller 入口统一拦截。
  - 前端校验只是体验优化，后端校验才是安全边界。

- **接口契约先行**
  - 后端先把新字段写进接口文档/DTO，前端不必等后端改完，可并行开发。
  - 联调时逐项对齐：字段名、类型、空值语义（null 还是空字符串），不猜字段、不造别名。

- **常见易错点**
  - 只改 Entity 忘了改 DTO：接口返回里永远看不到新字段。
  - 忘了写迁移脚本：本地能跑，测试环境一查就报"列不存在"。
  - 新字段可空但代码直接使用：历史数据全是 null，线上直接 NPE。
  - 前端在字段未上线时就渲染：出现 undefined 闪屏，前端要做兜底渲染。

- **交付链路思维**
  - 改动的最小单元不是"一个文件"，而是"一条贯穿所有层的链"。
  - review 时沿这条链逐层检查，比只看最后一段 diff 可靠得多。
