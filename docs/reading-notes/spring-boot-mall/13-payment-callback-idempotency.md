# 第 13 篇：支付成功不等于结束：回调、幂等、超时关单和状态竞争

> 原文：[支付成功不等于结束：回调、幂等、超时关单和状态竞争](https://juejin.cn/post/7667847028815249471)，作者 swipe，《从前端到全栈：Spring Boot 项目实战通关》。
>
> 本笔记是蒸馏版，只保留核心问题、概念和结论，细节请读原文。

## 核心问题

前端人容易以为"支付接口返回成功，支付流程就结束了"。但支付真正的难点在接口返回之后：第三方回调可能重复、乱序、丢失，用户可能迟迟不支付。这篇文章回答的是：支付结果真正落地的最后一公里，服务端要怎么安全地走完？

## 关键要点

- **支付结果不能信前端**
  - 用户支付动作发生在第三方（微信/支付宝），前端跳转到"支付成功页"只是展示层信号。
  - 唯一可信的结果来源是第三方服务器主动发来的回调（notify），服务端必须以回调为准落库。
  - 回调处理完要按第三方协议返回应答，否则对方会认为失败并继续重发。

- **回调天然不可靠，处理必须幂等**
  - 第三方会重发回调：同一笔支付的通知可能到达 N 次，甚至乱序。
  - 幂等的关键是为每笔支付准备唯一流水号（outTradeNo / requestId）。
  - 落地三板斧：数据库唯一约束兜底；先查状态再处理；状态变更用条件更新：

  ```sql
  UPDATE orders SET status = 'PAID'
  WHERE order_no = ? AND status = 'UNPAID';
  -- 受影响行数为 0 说明已被处理，直接按幂等成功返回
  ```

  - 重复回调不走重复发货、重复加积分等副作用，直接返回成功。

- **回调必须验签**
  - 校验第三方签名，防止攻击者伪造"支付成功"回调白拿商品。
  - 验签失败直接拒绝，不进入业务逻辑。

- **超时关单：不支付的订单要有人收尾**
  - 订单创建后长期不支付会一直占库存/占单号，需要过期机制。
  - 典型实现：给订单设超时时间，用定时任务扫描、延迟队列或 Redis 过期事件把订单置为"已关闭"。

- **状态竞争：关单和回调赛跑**
  - 用户在关单前一秒支付成功，回调与关单任务几乎同时执行。
  - 解决思路与幂等同源：任何状态变更都声明前置条件——只在 `UNPAID` 时允许关单，也只在 `UNPAID` 时允许标记已支付，行级更新保证只有一个方向生效。
  - 另一个方向失败后要能感知并收尾：如"已关单才收到回调"需进入退款/对账流程。

- **状态机思维**
  - 把订单生命周期定义为有限状态：待支付 → 已支付 → 已发货…，或待支付 → 已关闭。
  - 每次变更声明"从哪个状态到哪个状态"，非法流转直接拒绝，比散落的 if-else 可靠得多。

- **对前端的启示**
  - 支付成功页是乐观展示，真实结果以轮询/推送查到的服务端状态为准。
  - 接口返回"订单已关闭"时应引导用户重新下单，而不是当错误抛出。
